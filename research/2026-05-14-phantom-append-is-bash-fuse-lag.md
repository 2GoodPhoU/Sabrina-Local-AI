## What I found

The evidence directly refutes the PROPOSED #41 "write-side divergence" reading and supports the H2 "read-side lag" reading. The spec-writer 2026-05-13 06:50 appends durably landed on canonical NTFS; the night-auditor 02:37 audit read through the stale bash-side FUSE cache and reasoned from a 21-hour-old snapshot of NEEDS-INPUT.md.

**Edit-tool write succeeded canonically.** The Read tool view of NEEDS-INPUT.md at this investigation's wall-clock (2026-05-14 ~03:30 PT) shows both `[from: spec-writer / 2026-05-13 06:50]` entries verbatim at lines 238 (expression-slot binding) and 247 (placeholder rig commit policy), with the `Recommendation: (a)` lines at 245 and 254 — exactly matching the spec-writer JOURNAL entry's claim of "two NEEDS-INPUT entries (P4.A3 expression-slot binding constant-vs-toml-vs-JSON / placeholder rig commit policy runtime-only-vs-LFS-vs-download)." Grep tool confirms `^- \[ \]` count = 29, matching the spec-writer's "27 → 29" claim. Both verifications use tool-channel reads, which per `research/2026-05-09-fuse-divergence-pattern.md` H2 are authoritative for canonical NTFS state.

**Bash view is stuck ~21 hours behind canonical.** `stat NEEDS-INPUT.md` via bash reports mtime 2026-05-13 02:47:00 UTC. The spec-writer 5/13 06:50 PT entry's wall-clock is approximately 5/13 13:50 UTC, ~11 hours after the bash-visible mtime. Tonight's night-auditor 02:37 PT ≈ 5/14 09:37 UTC, ~21 hours after the bash-visible mtime. The file content bash returns is the pre-spec-writer-write version: `wc -l` 236 lines, `^- \[ \]` 27 matches, `tail -5` ending at the P4.A2 entry's terminal line — which is the exact line the spec-writer named as its anchor for the appends. Three independent bash commands (`wc -l`, `grep -c`, `tail -5`) all report this stale snapshot; the divergence is read-channel-wide, not specific to one bash command. The night-auditor 02:37's "zero matches" grep was correct against the bash view and correctly described what bash saw — but bash was wrong relative to canonical NTFS.

**The stale-view persistence is the new finding.** `research/2026-05-09-fuse-divergence-pattern.md` documented lag of "four entries (~22011 bytes, multiple hours of writes) invisible to Python within the same session" and "~73 lines invisible to bash within the same hour" — both within-session observations. This finding extends the H2 envelope: the bash-side FUSE cache lagged the spec-writer 5/13 06:50 write by **21+ hours** and across **at least four chain handoffs** (spec-writer → planner → graduation-sweeper → digest → night-auditor). The lag survived process restarts (each scheduled task is a fresh sandbox session), survived the file mtime advancing on canonical (mtime is what bash itself sees frozen at 5/13 02:47 UTC), and was not invalidated by any read or stat operation. This is a stronger version of the 2026-05-09 H2 finding ("lag is not bounded by minutes") — lag is also not bounded by sessions, days, or chain rotation.

**Asymmetric write semantics confirmed.** The spec file (`rebuild/drafts/research/2026-05-13-p4a3-avatar-live2d-rig-bind-spec.md`) IS visible to bash with mtime 2026-05-14 00:38 UTC — bash sees writes to this path. So the divergence is not "all canonical writes are invisible to bash"; it's per-file: bash sees the spec-file write (a new file) but not the NEEDS-INPUT.md Edit-anchor write (a modification to an existing file with cached content). This matches the 2026-05-09 finding's "Reads via Python/bash → through FUSE cache, which lags canonical" — the cache lag is per-file content, not per-mount global. Newly-created paths get fresh cache entries; existing paths can keep their stale entry across the canonical write.

**PROPOSED #41 evidence reversal.** PROPOSED #41 names three hypotheses for the apparent phantom: (a) separate root cause from worker-9am 2026-05-07 (which involved Python `read() + os.replace()`), (b) Edit-tool-with-anchor has its own divergence window under sandbox-FUSE-lock contention, or (c) something rolled back the change after Edit returned success. The evidence I gathered rules out all three: (a) the worker-9am 2026-05-07 root cause was Python read returning stale FUSE-cached content — same root cause as tonight's bash-grep returning stale FUSE-cached content; (b) Edit-tool-with-anchor wrote durably (the canonical-NTFS view via Read confirms; the spec-writer's anchor was unique pre-write and the appends are present post-write); (c) no rollback occurred — the canonical content is what the spec-writer wrote, intact, 21 hours later. The night-auditor's reasoning chain ("the anchor used is still single-occurrence in the file (count = 1) and still the terminal-line of the last NEEDS-INPUT entry — so the Edit didn't append after it") implicitly assumes bash-grep == canonical. Under H2 that assumption fails: bash-grep saw the pre-write snapshot where the anchor IS still the terminal line because the write isn't yet visible to bash; meanwhile in the canonical view (Read tool) the anchor is no longer terminal — lines 238-254 follow it.

**Cross-tool inconsistency in the night-auditor's own audit.** The night-auditor 02:37 entry explicitly noted live H2 divergence on JOURNAL.md the same run ("Live H2 echo also observed this run: `wc -l JOURNAL.md` via bash returned 1010 lines (...) but Read tool sees through line 1063") and trusted Read view for that file. The audit then used bash-grep as the primary verification path for NEEDS-INPUT.md without applying the same Read-tool fallback. This is the load-bearing process gap PROPOSED #41 should be reframed around: not "Edit-tool-with-anchor has a divergence window," but "verify-post-Edit needs to consistently use the tool channel; mixing bash-grep into the verification path reintroduces the H2 lag."

**Downstream chain drift was real but the cause is different.** PROPOSED #41's "downstream chain entries (5/13 graduation-sweeper, digest, worker-8am, worker-10am) all inherited the phantom 29 / 23 counts" observation is partially correct in direction but inverts cause: those downstream entries inherited the correct 29 / 23 counts from the spec-writer's accurate JOURNAL claim, propagated via STATE.md narrative; the night-auditor 02:37 then read the bash-stale view and (re)introduced the wrong 27 / 21 counts, claiming the downstream entries were drifted-wrong. They weren't. The night-auditor's own counts are the drift-wrong reading. STATE.md narrative "23 spec-writer (a)-half NEEDS-INPUT picks consolidated under S11(a)" and the related "27 → 29" framing in the spec-writer entry are correct; the night-auditor entry's "true count is 27 / 21" finding is incorrect.
